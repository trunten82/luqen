# Requirements Archive: v3.9.0 Dismissal follow-through

**Archived:** 2026-10-21
**Status:** SHIPPED

Public summary: one line of shipped behaviour per requirement. HARD-20 was not assigned.


## Scanning

- [x] **SCAN-01**: A scan created through the GraphQL `createScan` mutation starts and reaches a terminal state (completed/failed), exactly like a scan started from `/scan/new` — it is never left `queued` forever.
- [x] **SCAN-02**: GraphQL `createScan` applies the same validation and limits as `/scan/new` (URL and private-target guard, organization scope, permission, page concurrency 1-10, jurisdiction cap, and the shared limit of 30 scan starts per 10 minutes) through one shared code path, so an input refused on one path is refused on both.

## Dismissal and permission hardening

- [x] **HARD-01**: The disabled Dismiss button refuses every selector the server validator refuses, including selectors over the 4000-character limit, so no user reaches an endless "Try again" loop.
- [x] **HARD-02**: A user without `reports.view_technical` never receives an issue's raw selector in the report DOM or in a request they trigger from the Dismiss/Assign controls.
- [x] **HARD-03**: Marking and previewing a dismissal require `reports.view` as listing does, so a role holding only `issues.dismiss` cannot act on or probe reports it cannot open.
- [x] **HARD-04**: i18n placeholder substitution treats values literally — a key label containing `$&`, `` $` `` or `$'` renders unchanged.
- [x] **HARD-05**: Dismissed/revoked dates render in the viewing user's session locale, not the server's.
- [x] **HARD-06**: The dark-permission filters (`withoutDarkPermissions`, `isRoleGrantablePermission`, `getPermissionGroups`) accept an injectable set and keep one red/green test per path, so they are watched even while `DARK_PERMISSIONS` is empty.
- [x] **HARD-07**: The remote dismissal UAT harness refuses to run unless pointed at a dedicated UAT org/site, and the README says so.
- [x] **HARD-08**: A dismissal made by an API key stays attributable after the key is deleted, and two keys with the same label are distinguishable in the Dismissed section.
- [x] **HARD-09**: The at-rest key-invariant test anchors on the wiring call expressions in `server.ts`, not on absolute line numbers.
- [x] **HARD-10**: Every state-changing `/api/v1/*` route reachable with a session cookie enforces CSRF; an inventory test enumerates the routes and fails when a new cookie-reachable write route is added without CSRF enforcement (cookie-CSRF sweep).
- [x] **HARD-11**: The dismissals list API returns exactly the rows the report page's Dismissed section shows for the same user and scan, including system scans — read access uses a read-side predicate, not the write-side one.
- [x] **HARD-12**: `issues.dismiss` can only be granted to org-scoped roles; an attempt to put it on a global/system role (including the built-in `user` role) through `/admin/roles` is refused.
- [x] **HARD-13**: MCP user create/update tools accept only valid role names and fully validated usernames (same rules as the dashboard), refusing anything else with a clear error.
- [x] **HARD-14**: Every path that starts a scan — scheduled scans, schedule create/update (`POST /schedules`), report retry and startup recovery — applies the same start-URL validation as `/scan/new` (SSRF/private-target and DNS guard), so a refused URL can never start through a second path.
- [x] **HARD-15**: Scans started through the MCP `dashboard_scan_site` tool draw from the same shared scan-start limit (30 per 10 min per caller) as `/scan/new` and GraphQL, without breaking org users of the agent bridge (who carry an empty permission set).
- [x] **HARD-16**: Team create and team org-move refuse a target organisation the caller may not administer (no team can be placed or moved into a foreign org by a non-global caller).
- [x] **HARD-17**: Global-only permissions (admin.system, admin.users) cannot be granted through org roles or team-bound built-in roles, are dropped at permission resolution for non-global users, and the MCP user tools assign the global admin role only for a stored active global admin (with the dashboard's org-scope and last-active-admin rules).
- [x] **HARD-18**: Every path that deletes a scan (REST, GraphQL and the report page) applies one shared rule: the caller holds `reports.delete` or is the signed-in user who started the scan, and the scan is in the caller's current organization.
- [x] **HARD-19**: The MCP endpoint resolves its caller from the stored user row on every request: a token for a missing or deactivated user, a revoked client, or an empty permission set is refused, and permissions come from the stored role, never a token claim.
- [x] **HARD-21**: A signed-in session and an MCP token re-check the stored user on every request: a demoted, deactivated or removed user loses the old role, org and access at once; the session's current org must still be one of the user's orgs; mcp.use is enforced per request; refresh refuses a missing or inactive user.

## Documentation

- [x] **DOCS-01**: User documentation in `docs/` explains how to mark a finding as a false positive, what the required reason is for, and who can do it (Owner/Admin and custom roles granted `issues.dismiss`).
- [x] **DOCS-02**: The documentation explains the effects of a dismissal — excluded from counts, score, exports and ACR/VPAT (with per-criterion disclosure), re-applied on later scans — and how to revoke one and read its audit history.
- [x] **DOCS-03**: The documentation is reachable from the docs index/README navigation and every procedure in it is executable as written against the shipped UI (verified by a cold read by a different agent).
